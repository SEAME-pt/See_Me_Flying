# See Me Flying: Study Guide

A walkthrough of everything in this repo: what each piece is, why it exists, and how the pieces connect. Read it top to bottom once, then use it as a reference.

---

## 1. The big picture in one paragraph

We are building the software for a drone. Today it flies **only in a simulator** (Gazebo). A small Python program invents velocity commands ("go up", then "fly in a circle"). A C++ program called `fc_bridge` checks those commands, limits them to safe speeds, and sends them to the simulated drone. If the commands stop coming, `fc_bridge` makes the drone stop and hover. A second C++ program, the `watchdog`, only watches and complains in the log when commands stop. Everything runs inside a **Docker container** so that every teammate has the identical environment (Ubuntu 24.04 + ROS 2 Jazzy + Gazebo Harmonic).

```
  setpoint_pub ──► fc_bridge ──► ros_gz_bridge ──► Gazebo (drone X3)
  (Python)          (C++)         (translator)      (simulator)
  "what I want"     "is it safe?" "ROS ↔ Gazebo"    "physics"
        │
        └──► watchdog (C++) — only listens, only logs
```

Later, `fc_bridge` will get a second backend that talks to the **real** flight controller (INAV) instead of Gazebo. The rest of the stack should not need to change: that is the whole point of having one "bridge" node.

## 3. The Docker layer

### Why Docker?

ROS 2 Jazzy officially needs Ubuntu 24.04. Teammates run different systems (Ubuntu 22.04 to 26.04, Arch). Instead of everyone installing ROS by hand and getting slightly different setups, everyone runs **the same container**. It also lets CI use the exact same environment.

### `Dockerfile`: the recipe for the image

```dockerfile
FROM ros:jazzy                      # official image: Ubuntu 24.04 + ROS 2 Jazzy base
```

| Section | What it does |
|---|---|
| `apt-get install ... ros-jazzy-ros-gz ...` | Installs Gazebo Harmonic + the ROS↔Gazebo bridge, plus dev tools (`ros-dev-tools` = colcon, rosdep), demos, turtlesim, rqt_graph, teleop keyboard, tf2 tools, git, vim |
| `userdel ubuntu`, `useradd ... dev` | Creates a user `dev` with **your** host UID/GID, so files written into the mounted `ros2_ws/` belong to you, not to root |
| `NOPASSWD` sudoers line | `dev` can `sudo` without a password inside the container |
| `mkdir /tmp/runtime-dev` | Folder Qt (Gazebo's GUI toolkit) needs, silences a warning |
| `.bashrc` lines | Every shell auto-sources ROS (`/opt/ros/jazzy/setup.bash`) and our workspace (`install/setup.bash`, if it exists) |
| `CMD ["sleep", "infinity"]` | The container just stays alive; you `exec` into it to work |

**Image vs container:** the *image* is the frozen recipe result (`docker compose build`). A *container* is a running instance of it (`docker compose up`). Changing the Dockerfile requires rebuilding the image.

### `compose.yaml`: how to run it

| Setting | Why |
|---|---|
| `build.args: HOST_UID/HOST_GID` | Passes your IDs (from `.env`) into the Dockerfile |
| `network_mode: host` | Container shares your machine's network, so ROS nodes find each other across containers and laptops (DDS discovery uses multicast) |
| `ipc: host` | Lets ROS use fast shared-memory transport |
| `DISPLAY`, `/tmp/.X11-unix` volume | Lets Gazebo draw its window on your screen (X11) |
| `ROS_DOMAIN_ID` | ROS "channel number". Same number = can talk. Different teams use different numbers so they don't see each other's topics |
| `./ros2_ws:/home/dev/ros2_ws` | **Mount**: the folder on your laptop *is* the folder in the container. Edit on the host, build inside |
| `/dev/dri` + `group_add video/render` | GPU access for Gazebo. Without it Gazebo falls back to slow software rendering |
| `init: true` | Proper signal handling so Ctrl+C / stop works cleanly |

### `make-env.sh` and `.env`

`make-env.sh` writes `.env` with your `HOST_UID`, `HOST_GID`, `ROS_DOMAIN_ID`, `VIDEO_GID`, `RENDER_GID`. Compose reads `.env` automatically. `.env` is personal and **must not be committed** (it's in `.gitignore`).

### Daily commands

```bash
# host
xhost +local:                 # allow container windows on your screen (after each login)
docker compose up -d          # start
docker compose exec dev bash  # open a shell inside (repeat for more terminals)
docker compose down           # stop

# inside the container
cd ~/ros2_ws
colcon build --symlink-install
source install/setup.bash
ros2 launch drone_bringup sim.launch.py
```

## 4. ROS 2 concepts you need

| Concept | Meaning | Example here |
|---|---|---|
| **Node** | One running program that does one job | `fc_bridge`, `watchdog`, `setpoint_pub` |
| **Topic** | A named channel. Publishers write, subscribers read. Many-to-many, no reply | `/fc/setpoint_velocity` |
| **Message type** | The data structure sent on a topic | `geometry_msgs/TwistStamped` |
| **Publisher / Subscriber** | A node's handle to write / read a topic | `create_publisher`, `create_subscription` |
| **Timer** | Calls a function periodically | `watchdog` checks every 100 ms |
| **Parameter** | A named setting of a node, changeable at launch or live | `timeout_s`, `max_speed_xy` |
| **QoS** (Quality of Service) | Delivery rules: *reliable* (resend lost messages) vs *best effort* (drop them), queue depth | `SensorDataQoS()` = best effort |
| **Remapping** | Rename a topic from outside the code | `setpoint_velocity` → `/fc/setpoint_velocity` |
| **Launch file** | Python script that starts several nodes with their settings | `sim.launch.py` |
| **Package** | Unit of code + build info (`package.xml`) | `drone_fc_bridge` |
| **Workspace** | Folder with `src/` holding packages; built with `colcon` | `ros2_ws/` |
| **Sourcing** | `source install/setup.bash` tells your shell where built packages are | Without it: "Package not found" |
| **Sim time** | `use_sim_time: true` makes `now()` follow Gazebo's `/clock`, not the wall clock. Pause the sim → time stops for the nodes too | All our nodes in `sim.launch.py` |
| **Spin** | `rclcpp::spin(node)` / `rclpy.spin(node)`: loop forever handling messages and timers | every `main()` |

### Message types used

- **`geometry_msgs/Twist`**: a velocity. `linear.{x,y,z}` in m/s, `angular.{x,y,z}` in rad/s. `angular.z` = yaw (turning left/right).
- **`geometry_msgs/TwistStamped`**: a `Twist` + a `header` (timestamp + frame name like `base_link`).
- **`std_msgs/Bool`**: just `data: true/false`.
- **`rosgraph_msgs/Clock`**: simulation time.

**Relative topic names:** a name without `/` (e.g. `fc/setpoint_velocity`) is relative to the node's namespace. With no namespace it becomes `/fc/setpoint_velocity`. That's why launch files can remap or namespace them later (e.g. for two drones).

## 5. Full data flow

```
┌──────────────┐  /fc/setpoint_velocity   ┌─────────────┐  /X3/gazebo/command/twist  ┌───────────────┐  gz.msgs.Twist  ┌──────────┐
│ setpoint_pub │ ───────────────────────► │  fc_bridge  │ ─────────────────────────► │ parameter_    │ ──────────────► │  Gazebo  │
│  (Python)    │   TwistStamped, 10 Hz    │   (C++)     │   Twist, 20 Hz             │ bridge        │                 │  X3      │
└──────────────┘            │             │  clamp +    │  /X3/enable (Bool, 1 Hz)   │ (ros_gz)      │ ◄────────────── │  drone   │
                            │             │  timeout    │ ─────────────────────────► │               │   /clock        └──────────┘
                            ▼             └─────────────┘                            └───────────────┘
                     ┌──────────┐                ▲                                          │
                     │ watchdog │                └───────────── /clock (sim time) ───────────┘ (to every node)
                     │  (C++)   │  logs only
                     └──────────┘
```

Key idea: **commands go one way** (towards Gazebo), **time comes back** (`/clock`). Nothing else comes back yet: the drone's position, IMU and odometry exist in Gazebo but are not bridged into ROS.

## 6. Package by package

### 6.1 `drone_basics_py` → `setpoint_pub`

**File:** `drone_basics_py/drone_basics_py/setpoint_pub.py`
**Job:** pretend to be the future "mission" brain. Publishes velocity commands.

**Parameters**

| Name | Default | Read | Meaning |
|---|---|---|---|
| `rate_hz` | 10.0 | once at start | publish frequency |
| `speed` | 0.3 m/s | every tick (live) | circle speed |
| `takeoff_s` | 4.0 s | every tick | how long to climb |
| `climb_speed` | 0.3 m/s | every tick | vertical speed while climbing (4 × 0.3 = 1.2 m) |

**Walkthrough**

```python
class SetpointPub(Node):
    def __init__(self):
        super().__init__('setpoint_pub')              # node name
        self.declare_parameter('rate_hz', 10.0)       # ...and the other 3 params
        self.pub = self.create_publisher(TwistStamped, 'setpoint_velocity', 10)  # reliable, depth 10
        self.t0 = None                                # "time zero", set on first tick
        self.phase = None                             # last logged phase
        self.timer = self.create_timer(1.0 / rate, self.tick)
```

`tick()` runs 10×/s:

1. `now = self.get_clock().now()`. With sim time this is Gazebo time.
2. First tick ever → `self.t0 = now`. So time zero = when the sim clock started arriving, not when the process started.
3. `t` = seconds since `t0`.
4. **If `t < takeoff_s`** → `linear.z = climb_speed` (go straight up).
5. **Else** → horizontal circle:
   `x = speed·cos(0.5·tc)`, `y = speed·sin(0.5·tc)`.
   The velocity vector rotates at 0.5 rad/s with constant length `speed`, which traces a circle of radius `speed / 0.5` (0.6 m at default).
6. Publish with `frame_id = 'base_link'` (the drone's body frame).

`log_phase()` logs "Phase: takeoff" / "Phase: circle" only **when the phase changes** (no spam).

`main()`: init ROS → create node → spin → on Ctrl+C clean up.

**Packaging files** (Python packages are built with `ament_python` = setuptools):

| File | Purpose |
|---|---|
| `package.xml` | Name, deps (`rclpy`, `geometry_msgs`), test deps (linters, pytest), build type `ament_python` |
| `setup.py` | `entry_points` → `setpoint_pub = drone_basics_py.setpoint_pub:main` creates the `ros2 run drone_basics_py setpoint_pub` command |
| `setup.cfg` | Installs that script into `lib/drone_basics_py` where `ros2 run` looks |
| `resource/drone_basics_py` | Empty marker file so ROS's package index can find the package |
| `drone_basics_py/__init__.py` | Makes the folder a Python package |
| `py.typed` | Tells mypy the package has type hints |
| `test/test_*.py` | Linter tests (see section 9) |

### 6.2 `drone_basics_cpp` → `watchdog`

**File:** `drone_basics_cpp/src/watchdog.cpp`
**Job:** notice when setpoints stop. Logs only, commands nothing. Seed of the future `safety_manager`.

```cpp
Watchdog() : Node("watchdog")
{
  timeout_s_ = declare_parameter<double>("timeout_s", 0.5);
  last_rx_ = now();                                          // pretend we just got one
  sub_ = create_subscription<TwistStamped>(
    "setpoint_velocity", rclcpp::SensorDataQoS(),
    [this](const TwistStamped &) { last_rx_ = now(); });     // only remember WHEN
  timer_ = create_timer(100ms, [this]() { check(); });
}

void check()
{
  const double age = (now() - last_rx_).seconds();
  const bool stale = age > timeout_s_;
  if (stale && !stale_)      WARN("No setpoint for X s: a real failsafe would command hover");
  else if (!stale && stale_) INFO("Setpoints are back");
  stale_ = stale;                                            // remember for next tick
}
```

**Concepts in this file**

- **Lambda** `[this](const TwistStamped &) {...}`: an inline function. `[this]` lets it access the node's members. The message parameter has no name because the content is ignored.
- **Edge detection**: compare the new state with the previous one (`stale_`) and log only on a *change*. Without it you'd get 10 warnings per second.
- **Member handles** (`sub_`, `timer_`): must be stored, otherwise they're destroyed and stop working.
- **`SensorDataQoS`**: best effort. A best-effort subscriber can receive from both reliable and best-effort publishers.

The warning right after launch is **expected**: `setpoint_pub` starts 5 s later.

**Build files:** `package.xml` (deps `rclcpp`, `geometry_msgs`; test deps `ament_lint_auto`, `ament_lint_common`) and `CMakeLists.txt` (see section 8).

### 6.3 `drone_fc_bridge` → `fc_bridge` ⭐ most important

**File:** `drone_fc_bridge/src/fc_bridge.cpp`
**Job:** the **only** node allowed to command the drone. Today: sim backend (Gazebo). Later: INAV backend (real flight controller over Wi-Fi).

**Parameters**

| Name | Default | Meaning |
|---|---|---|
| `gz_twist_topic` | `/X3/gazebo/command/twist` | where commands go |
| `gz_enable_topic` | `/X3/enable` | where "enable" goes |
| `rate_hz` | 20.0 | output rate (read once) |
| `setpoint_timeout_s` | 0.3 s | older than this = stale |
| `max_speed_xy` | 0.5 m/s | horizontal speed cap |
| `max_speed_z` | 0.3 m/s | vertical speed cap |
| `max_yaw_rate` | 1.0 rad/s | turning-rate cap |

Timeout and limits are read every tick, so `ros2 param set` changes them live. They're doubles: write `2.0`, not `2`.

**Constructor**

- Declares parameters.
- Creates 2 publishers: `Twist` to Gazebo, `Bool` to enable.
- Subscribes to `fc/setpoint_velocity`. The callback stores the latest `twist` in `last_sp_` and the arrival time in `last_rx_`.
- Two timers: `tick()` at 20 Hz, `keep_enabled()` at 1 Hz.

**`tick()`: the decision every 50 ms**

```cpp
bool fresh = false;
if (last_rx_) {                                  // have we EVER received one?
  const double age = (now() - *last_rx_).seconds();
  fresh = age >= 0.0 && age <= param("setpoint_timeout_s");
}                                                // age < 0 happens if sim time was reset
// log only on change: "Setpoints received, following them" / "Setpoint timeout: holding"
stale_ = !fresh;
cmd_pub_->publish(fresh ? clamp(last_sp_) : Twist());   // Twist() = all zeros
```

**Why publish zero every tick?** Gazebo's X3 velocity controller keeps following the **last** command it received. If we simply stopped publishing, the drone would keep flying. The explicit zero is what makes it stop and hover. **That is the failsafe.**

**Why publish every tick even when nothing changed?** Same reason: Gazebo and later the real FC must constantly hear from us.

**`clamp()`: the safety limits**

```cpp
// Horizontal: scale x and y TOGETHER so direction is kept
norm  = hypot(x, y);                               // horizontal speed
scale = (norm > vmax && norm > 0) ? vmax / norm : 1.0;
out.x = x * scale;  out.y = y * scale;

out.z         = clamp(z,         -zmax, zmax);     // vertical
out.angular.z = clamp(angular.z, -wmax, wmax);     // yaw
// angular.x / angular.y (roll/pitch rates) are never copied → always 0
```

Example: input `(3, 4)` m/s → speed 5 → scale 0.1 → output `(0.3, 0.4)`, same direction, speed 0.5.
If you clamped x and y separately you'd get `(0.5, 0.5)`, which is a **different direction** and faster than 0.5. That's why the scaling approach is used.

**`keep_enabled()`**: publishes `true` on `/X3/enable` every second. Sim only. On the real drone, arming stays on the radio (a human decision).

**`std::optional<rclcpp::Time> last_rx_`**: "maybe a time". Empty until the first setpoint arrives, so "never received" is different from "received long ago".

### 6.4 `drone_bringup`: launch files and config

No code to compile. Its `CMakeLists.txt` just installs `launch/` and `config/` into `install/` so `ros2 launch` can find them. A new launch file is only visible after `colcon build`.

**`sim.launch.py`: the whole first flight**

| Action | What it starts |
|---|---|
| `IncludeLaunchDescription(... gz_sim.launch.py, gz_args='-r multicopter_velocity_control.sdf')` | Gazebo with the built-in world (2 quadcopters, X3 and X4). `-r` = run immediately (not paused) |
| `Node(ros_gz_bridge parameter_bridge, arguments=[...])` | The translator (see section 7) |
| `Node(drone_fc_bridge fc_bridge)` | with `use_sim_time: true` |
| `Node(drone_basics_cpp watchdog)` | remapped to `/fc/setpoint_velocity` |
| `TimerAction(period=5.0, Node(setpoint_pub))` | started 5 s later (wall time), remapped too |

The 5 s delay is wall time, but it's safe on slow machines anyway: `setpoint_pub` runs on sim time, so its clock doesn't start until Gazebo's `/clock` arrives.

**`basics.launch.py`**: currently the **same as `sim.launch.py` but without `setpoint_pub`**: Gazebo, bridge, `fc_bridge`, `watchdog`. Useful for flying manually (e.g. with `teleop_twist_keyboard`).
⚠️ The README still describes an older version (setpoint_pub + watchdog with `config/basics.yaml`, no Gazebo). The README is out of date here, and `config/basics.yaml` is currently not used by any launch file.

**`config/basics.yaml`**: example ROS parameter file format:

```yaml
setpoint_pub:            # node name
  ros__parameters:       # magic key ROS expects
    rate_hz: 20.0
```

## 7. Gazebo and the bridge

**Gazebo** (`gz sim`, version Harmonic) is a physics simulator. It is **not** a ROS node and has its **own** message system (`gz topic -l` lists its topics).

The world `multicopter_velocity_control.sdf` ships with Gazebo. SDF = Simulation Description Format (XML describing models, physics, plugins). The X3 drone has a built-in **velocity controller**: give it a `Twist` and it computes motor speeds to reach and hold that velocity. It only obeys while **enabled**.

**`parameter_bridge`** copies messages between ROS and Gazebo, only for the topics listed:

```
'/X3/gazebo/command/twist@geometry_msgs/msg/Twist]gz.msgs.Twist'
 └─ topic name ─────────┘ └─ ROS type ──────────┘│└─ Gz type ──┘
                                                 └ direction
```

| Symbol | Direction |
|---|---|
| `]` | ROS → Gazebo |
| `[` | Gazebo → ROS |
| `@` | both ways |

| Topic | Direction | Why |
|---|---|---|
| `/X3/gazebo/command/twist` | ROS → Gz | velocity commands |
| `/X3/enable` | ROS → Gz | enable controller |
| `/clock` | Gz → ROS | sim time for every node |

## 8. The build system

### colcon

`colcon build` goes through every package in `src/`, figures out the order from dependencies, and builds each one with its own tool (CMake for C++, setuptools for Python). Output:

- `build/`: intermediate files
- `install/`: final executables, launch files, `setup.bash`
- `log/`: build and test logs

`--symlink-install` links Python files and launch files instead of copying them, so Python edits are live without rebuilding. C++ always needs `colcon build`.

### `package.xml` (every package)

The package's ID card: name, version, maintainer, license, and dependencies.

| Tag | Meaning |
|---|---|
| `<buildtool_depend>ament_cmake` | build with CMake via ament |
| `<depend>` | needed to build **and** run |
| `<exec_depend>` | needed only to run (bringup uses this for the nodes it launches) |
| `<test_depend>` | needed only for tests |
| `<export><build_type>` | `ament_cmake` or `ament_python` |

`rosdep install --from-paths src` reads these tags and apt-installs whatever is missing.

### `CMakeLists.txt` (C++ packages)

```cmake
cmake_minimum_required(VERSION 3.8)
project(drone_fc_bridge)                         # must match package.xml name
set(CMAKE_CXX_STANDARD 17)                       # C++17 (std::optional, std::clamp)
add_compile_options(-Wall -Wextra -Wpedantic)    # extra warnings
find_package(rclcpp REQUIRED)                    # one per dependency
add_executable(fc_bridge src/fc_bridge.cpp)      # compile the program
target_link_libraries(fc_bridge PUBLIC rclcpp::rclcpp ${geometry_msgs_TARGETS} ...)
install(TARGETS fc_bridge DESTINATION lib/${PROJECT_NAME})   # where ros2 run looks
if(BUILD_TESTING) ... endif()                    # tests, only when testing
ament_package()                                  # must be last
```

### How `ros2 run pkg exe` finds things

It looks in `install/<pkg>/lib/<pkg>/<exe>`. That's why both `install(TARGETS ...)` in CMake and `setup.cfg` in Python point to `lib/<package_name>`.

## 10. Git, review and CI (ticket STK-4)

**Goal:** one repo, every change reviewed, and an automatic build + test on every push. Done when the 4 packages are on `main` and CI is green there.

| Sub-task | Meaning | Status |
|---|---|---|
| STK-4.1 Repository | Code in git; `build/ install/ log/` ignored; 4 packages pushed | Mostly done (on branch, not yet on `main`) |
| STK-4.2 Rules | Branch naming convention, PR template, ≥1 reviewer, protected `main` | To do (GitHub settings + `.github/pull_request_template.md`) |
| STK-4.3 GitHub Actions | `.github/workflows/ci.yml` runs `colcon build` + `colcon test` inside the Docker image | To do (old `CI-workflow` branch uses Humble/22.04, wrong) |

**CI flow:**

```
push / PR ─► GitHub runner (fresh VM)
              ├─ checkout
              ├─ docker build seame-docker   (same image as your laptop)
              └─ docker run ... :
                   rosdep install → colcon build → colcon test → colcon test-result
              ─► ✅ or ❌ on the commit/PR
```

`colcon test` always exits OK even if tests fail. **`colcon test-result --verbose` is what makes CI red.**

### Tests the CI should have, by priority

1. **Lint** (exists): keep it passing, turn cpplint/copyright back on.
2. **Unit tests of `fc_bridge`**: clamp keeps direction and caps speed; z/yaw limited; roll/pitch zero; freshness (no setpoint, too old, negative age = stale).
3. **Integration test of the failsafe**: start `fc_bridge`, publish, stop publishing → output becomes zero.
4. **Unit tests** of `setpoint_pub` phases and `watchdog` edge detection.
5. **Launch smoke test**: launch file starts and nodes stay alive.
6. *(later)* headless Gazebo test, nightly.

To unit-test, the logic must first be **extracted from the node classes** into plain functions (e.g. `clamp(twist, limits)`, `is_fresh(age, timeout)`), because right now it's private and tied to ROS parameters.

## 11. Known issues (from README)

| Issue | Why it matters | When |
|---|---|---|
| NaN/infinite values pass through the clamp | NaN comparisons are always false → NaN forwarded to the drone | Before hardware |
| Enable published forever | Fine in sim; on hardware ROS must not arm the drone | Before hardware |
| Message timestamp ignored | A delayed message still counts as fresh | Before hardware |
| No state comes back (pose, IMU, odometry) | Can't check height/position or close a loop | Next |
| Takeoff is timed, not measured | Real height unknown | Next |
| Never lands | Flight ends only by Ctrl+C | Next |
| Velocity frame not verified | `base_link` vs world frame may differ when yawed | Next |
| Timeouts disagree (watchdog 0.5 s vs fc_bridge 0.3 s) | Watchdog warns after the drone already stopped | Later |
| No namespaces | Two drones would clash | Later |
| Gazebo models downloaded inside container | Lost on recreate, needs internet | Later |

- `drone_interfaces` package for custom messages (`FcStatus`).
- `fc/arm`, `fc/hold` services.
- `backend` parameter: `sim`, `inav`, `mock`.
- **INAV backend**: MSP (MultiWii Serial Protocol) over the ESP8266 Wi-Fi link.
- **`safety_manager`** node (grows from the watchdog): hover on timeout, return on low battery.
- **`mission`** node (replaces `setpoint_pub`): takeoff, waypoints, landing as an action server.
